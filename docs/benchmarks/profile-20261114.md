# CPU speed, second round (2026-11-14)

Continues [profile-20261014.md](profile-20261014.md). The measure is the
portable UnixBench harness (`byte-unixbench`, branch `portable-harness`,
`UnixBench/portable/release/ubench-sparc-netbsd-v8`): Dhrystone 2 and
Whetstone, index 10 = SPARCstation 20-61 (116,700 lps, 55.0 MWIPS).

## Measuring: kill makemandb first

The board's `netbsd11.raw` starts `makemandb -Q` at boot; it runs for
minutes and takes about 40 % of the CPU. Figures taken right after login
are low by that much (49.6k lps / 17.7 MWIPS instead of 84.4k / 30.4 on
the same bitstream). `pkill makemandb`, check with `ps ax`, then measure.
QEMU shows the same.

One CPU is measured: the tests are single-threaded and NetBSD under
OpenBIOS runs one processor.

## Where the gap to the SS20-61 is

- The binary: 473 instructions a Dhrystone loop (V8 build; 514 for V7),
  counted in QEMU with `-icount shift=0` (lps = loops per 1e9
  instructions). 57 % of them are NetBSD libc's `strcmp` (a byte loop,
  9 instructions a byte) and `memcpy`. Whetstone: 612k instructions a
  "million Whetstone instructions", 76 % of the time in libm (N5 trig,
  N8 exp/log); no sqrt is executed (`-ffast-math` folds it).
- The clock: 55 MHz. The pipeline's paths (cache load, forward + ALU,
  memory request) are all about 17.5 ns.
- One instruction a cycle at best; the SuperSPARC issues up to three.

## Changes (commits 372e398, bce7416, d518e7d)

perfbench ticks, one-CPU sim (lower is better):

```
kernel   6779d22   372e398 (FPU)   bce7416
DHRY       67275       67275        56144
COPY       76415       76415        57350
ZERO       57327       57327        57327   (one instruction a cycle already)
CHASE     123409      123409       119770
SORT      128552      128552       109196
FP         69899       60584        51411
```

- Fetch: a two-entry buffer (no empty cycle after a stall of D).
- Prediction: an eight-entry return stack; a 512-entry history of
  two-bit "against the static direction" counters. Redirects in
  Dhrystone: 6 % of cycles -> 1 %.
- Stores: the write buffer joins stores to the doubleword of its newest
  entry; a store of a just-loaded word takes its data from W.
- FPU: no register between the result and the rounder; the next FPop is
  taken while the previous one rounds (no trap enabled, no dependence).
  Multiply 5 -> 3 cycles back to back, add 6 -> 4.

## 65 MHz

`scratch/clk.sh 65` sets the PLL (clk_sys and its 270-degree copy; the
pixel clock gets a phase so that the two 65 MHz counters stay apart, the
SDC wants both) and `CLK_HZ`; `scratch/clk.sh 55` restores the tree.
Nothing else needs the frequency.

As built from d518e7d (seed 1, 98 % full): -2.03 ns on the CPU clock.
On the board: cpu 84/0/5 twice, netbsd, solaris, video (OpenBIOS text,
CDE login), 15 minutes of stress with both CPUs. Not run: post, scsi,
cd, net. One board, room temperature.

A one-CPU build (70 % full) still misses by 1.71 ns: it is logic depth,
not congestion. The paths, all between -1.8 and -2.0 ns:

1. **Data load**: micro-TLB match -> ppn -> the cache's tag compare ->
   way select -> lane shift -> `w_rdata`; the same front end into the
   stall chain (ack -> m_go -> e_go -> d_go -> f_take -> f_pc/f_npc).
2. **Execute**: forward -> ALU -> `m_result`, with the micro-TLB match
   retimed behind it.
3. **Fetch**: I-cache tag compare -> way select -> the word -> the
   prediction's decode and target adder -> `f_npc`.
4. **Memory request**: a cache's state -> the module's port owner ->
   ss20_mbus's master select and request mux -> emc's entry match.

### Cut 1 (done): the data micro-TLB a cycle ahead

The lookup is made in E on the page of the base register (rs1's, or
rs2's when rs1 is only an offset within a page), beside the adder, and
registered with the physical page; M uses it when its page is the
address's and otherwise waits one cycle for the lookup of its own page.
Paths 1 and 2 leave the list: the CPU alone (`scratch/cputiming.sh TAG
15.384`) goes from -1.47 ns to -0.81 ns, total negative slack -124 ->
-12 ns, and what is left is path 3 only. Cost: perfbench unchanged but
CHASE +3 % (a large index leaves the base's page every time).
The full design at 65 MHz (seed 1) is still at -2.18 ns, on paths 4 and 3
now (total negative slack -705 -> -220 ns), with the FPU's FsTOd/FdTOs
operand -> the rounder's tininess test behind them at -1.6 ns (the
register the FPU change of bce7416 removed; put one back for that op).
Board at 65 MHz: cpu 84/0/5 twice, netbsd, solaris.

(Selecting the I-cache's way by its one-hot match instead of an index
did not help: -1.35 ns in the same fit. Reverted.)

### Next

- **Path 3: a branch target buffer.** The next fetch address from a
  small RAM read with the pc, in the cycle of the I-cache access, with
  no dependence on the word; D checks it against the decoded instruction
  and redirects on a mismatch (one bubble). Replaces the decode and
  adder between the cache and `f_npc`.
- **Path 4: a register between the CPU module's memory port and
  ss20_mbus** (the request held until its acknowledge; one cycle more a
  miss), or the entry match of emc from a registered address.
- Then a full build, the board tests, and a decision on the clock.
- Left from before: SAVE/RESTORE still wait for the pipeline to drain
  (about 2 % of Dhrystone, more in call-heavy code); a load's use still
  costs a bubble (4 %).

## After the release: the 65 MHz paths, one by one

Full design, 65 MHz, seed 1 (worst slack on the CPU clock, total negative
slack):

```
aeef267  the release                                   -2.18 ns   -220 ns
4e541fe  + mbus request register, fp_round tininess    -1.74 ns            94 % full
6cdaf7b  + branch target buffer                        -0.92 ns    -15 ns  (the worst: scsi_targets cdb -> st)
this     + cdb two cycles (SDC), pr_now, RAS a cycle   -1.02 ns    -41 ns  98 % full
         later
```

(The last two are within a fit's noise of each other; the SCSI path is
gone, the others moved up.) What is left, all between -0.6 and -1.0 ns:

- M's forwarding into E's check of a predicted return or target, and on
  into `f_pc`; the same start into the I-cache's state through
  `ifetch_req_o.ready`.
- The registered physical page -> tag compare -> way select -> lane
  shift -> `w_rdata` (the load path, 0.9 ns over).
- FPU: an operand's compare -> normalise -> the rounder's `t_low/t_edge`.

Cost of the cuts on the board (Solaris 8, V8 binary, 65 MHz): Dhrystone
133,548 -> 129,804 lps, Whetstone 46.3 -> 45.6 MWIPS (a cycle more a
cache miss; a redirect the first time a transfer is taken). Board with
6cdaf7b: cpu 84/0/5 twice, netbsd, solaris, 15 minutes of stress; with
this commit: cpu 84/0/5 twice, netbsd, solaris.

Ideas for the rest: the redirect a cycle later for a mispredicted return
(rare); the lane shift and sign extension behind `w_rdata` for loads
that nothing forwards from in the next cycle; a register in front of the
FPU rounder for FsTOd/FdTOs only; another fitter seed.

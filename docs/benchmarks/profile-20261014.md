# Where the new core's cycles go (2026-10-14)

A cycle-by-cycle profile of the CPU under NetBSD, to decide how to make
the core about twice as fast (UnixBench index 2.6 single-CPU under
OpenBIOS, [unixbench.md](unixbench.md); a real SS20 Model 50 would be
about 7-8).

## Method

- **Detailed profiling in the simulation, quick checks on the board**
  (the user's rule): the sim is deterministic and sees every cycle but
  its DDR is a model (about 8 memory-controller cycles a request); the
  board has the real HPS-bridge DDR latency, but its timings vary
  +-10-20 % between passes.
- `+perf` (rtl/cpu/iu.sv, simulation only): every cycle of each IU is
  given to the oldest pipeline stage that explains it: a commit (user or
  supervisor), W's second cycle, M waiting for a load / a store or atomic,
  E waiting for mul/div, D held for an FP op in flight / another hazard
  (load-use, serialising), D empty ("fetch": an I-cache miss, a taken
  transfer's redirect, a trap's refill), else "other". Printed every 10M
  cycles with taken transfers and traps.
- `+promlog` (rtl/machine/ss20_memctl.sv, simulation only): requests per
  CPU (writes, line reads), DVMA, the controller's busy share and cycles
  a request.
- `tools/perfsplit.py OUT [CPU]` splits that output into the phases a
  workload marks on the console (`echo M-NAME` between commands).
- The run: model 16938f1 + the intctl fix (`sim/obj_perf`), OpenBIOS
  07740ae3 (TMS390Z50 identity), the UnixBench image
  (`netbsd11-ub.raw`, GENERIC, one CPU used), after login:
  `dhry2reg 2; whetstone-double; spawn 2; execl 3; fstime -c -t 2 ...;
  pipe 2; context1 2; syscall 2; looper 3 multi.sh 1`, each preceded by
  its marker. About 10G cycles, 6 hours at ~0.5 MHz.
  ```
  sim/obj_perf/Vsim_top --rom openbios-z50.rom --nvram <openbios-fmt copy> \
    --hd0 <netbsd11-ub.raw copy> --cycles 12G --progress +perf +promlog \
    --send 'login: =>root\r' --send 'sunsparc# =><the commands>\r' \
    --stop M-END --log nb-perf.log > nb-perf.out
  python3 tools/perfsplit.py nb-perf.out 0
  ```

## What the RTL says the buckets are

- **Load wait 15-24 %.** l1cache: "a read hit answers in the cycle after
  the request"; the IU's M stage holds until the answer, so every load,
  hit or miss, costs at least one extra cycle. Dhrystone (fits in the L1)
  still loses 17 % here.
- **Store wait 7-14 %.** The D-cache is write-through with no store
  buffer: the CPU side "holds req_i until done_o", so every store waits
  for its memory write. Writes are 45-77 % of all memory requests. On the
  board (slower DDR than the sim's model) this is worth more.
- **Fetch 12-28 %.** I-cache misses and the bubble after taken transfers
  (the redirect resolves in E). Worst in the fork/exec, file and shell
  tests (more distinct code).
- **FP 24 % in Whetstone.** FP instructions go one at a time (iu.sv: "the
  next waits in D until the one ahead has left W and the FPU is idle").
- **Other 11-16 %.** Not yet split (D valid, not hazard, E/M not waiting:
  e.g. W's trap handling, M's I/O accesses, the gap after a redirect).
  Refine before acting on it.
- mul/div (0.2 %), W's second cycle (<1.5 %) and load-use hazards
  (3-6 %) are small.

## Plan: towards 2x

In order of expected gain for the effort:

1. **Store buffer** (D-cache side): stores retire into a small queue
   (4-8 doublewords, coalescing per line) that drains to memory in the
   background; loads check it (forward or wait on a match); atomics,
   uncached/I/O stores and MBus snoop rules still order correctly.
   Removes most of the 7-14 % store wait.
2. **Load hits without holding M:** return hit data so that only a
   dependent instruction waits (the usual one-cycle load-use bubble) --
   e.g. present the address in E so the hit answers by M. Most of the
   15-24 % load wait.
   Items 1 + 2 are 25-35 % of all cycles: CPI ~3.2 -> ~2.2 (1.4-1.5x).
3. **Fetch:** resolve taken branches earlier or predict them (a small
   BTB), prefetch the next I-cache line; look at the I-cache miss path's
   latency. Up to ~10-15 %.
4. **Split "other"** in +perf, then decide.
5. **FP overlap** (independent FP ops in flight): mostly Whetstone.
6. Memory side, after 1-3: a shared write-back L2 between ss20_mbus and
   ss20_memctl (128 KB of the 221 free M10K; ~2k ALMs) for the
   fork/exec/file tests. Measure first (the store buffer changes the
   store traffic it would absorb).

Every step: the unit benches, the CPU suite (sim and board), NetBSD and
Solaris boots, OBP POST, then UnixBench on the board for the speed and the
+perf profile in the sim for the cause. Room: 4.7k ALMs free (89 %); the
HDMI clock misses by ~0.15 ns already, so watch timing.

## Iterating fast: the perfbench ROM (tier 1)

Booting NetBSD in the sim takes hours, so pipeline experiments use a
bare-metal ROM instead: `tests/cpu/src/perfbench.S` runs
`tests/cpu/bench/` (UnixBench's Dhrystone 2.1, adapted only to run
freestanding, plus small kernels: page copy, page zero, a pointer chase
over 256 KB, an insertion sort, an FP multiply-add loop) with the MMU on,
cacheable and out of boot mode, the way a user program runs, each kernel
preceded by its `M-NAME` marker.

```
python3 tests/cpu/build.py ss20 --main=perfbench      # compiles bench/*.c with clang
SIM_NCPU=1 SIM_OBJ=obj_perf1 sim/build.sh             # one CPU (see below)
sim/obj_perf1/Vsim_top --rom tests/cpu/out/ss20/perfbench.rom --cycles 600M \
    --stop 'CPUTEST DONE' +perf +perf_period=1000000 > pb.out
python3 tools/perfsplit.py pb.out 0
```

About 45 s of simulation. Use the one-CPU model: with two, the suite's
runtime parks CPU 1 in the boot PROM, in boot mode, and its paced PROM
reads keep the memory controller 92 % busy (CPU 0's requests then take
25-43 cycles instead of ~8), which NetBSD's runs do not have (OpenBIOS
parks CPU 1 in a cached loop).

```

SORT       2.11          1.85                    1.79

```

- **Store buffer (50ff00b, on the board):** UnixBench 2.6 -> 2.8
  (Dhrystone 34.0k -> 39.8k lps, pipe +14 %, syscall +11 %), the CD boot
  123 -> 113 s; every board test passes; 38,202 ALMs, all clocks met.
- **FAST_ACK (iu.sv, uncommitted while the board round runs):** M moves on
  in the cycle its memory answer arrives instead of the next (the
  registered m_acked cost every load and store a cycle; it was most of
  "other"). sim/cpu 73/0/0 in all five modes. The cpu_module-alone fit
  had +3.85 ns before it. The FP kernel got 5 % slower (the one-at-a-time
  FP rule interacting with the earlier M exit): look at it with FP
  overlap (plan item 5).
- Still to do from the plan: the load's own two cycles in M (request,
  then the compare cycle), fetch (taken-branch redirects, I-cache
  misses), FP overlap, then the L2.

- **FAST_ACK on the board:** UnixBench 2.8 -> **3.0** (Dhrystone 44.8k
  lps; from 34.0k before both changes: +32 %), the CD boot 113 -> 109 s,
  every board test passes; 38,377 ALMs; cpu_module alone +2.74 ns.
- **The fork-heavy freeze: UnixBench's, not the core's (2026-10-15).**
  Caught on the board by scripts/board/forkloop.sh (pass 6, 44 min): in
  DDB the CPU was idle and taking clock interrupts (273k ticks), nothing
  runnable; `spawn` slept "parked" in _lwp_park called from ld.elf_so,
  with a zombie child, and `time` waited for it. QEMU's SS-20 with the
  same image freezes the same way in 5-11 minutes (spawn "parked", zombie
  child); LD_BIND_NOW=1 does not help. Cause: spawn and looper (shell1/8)
  end their run from SIGALRM with fprintf + exit; when the alarm lands
  inside fork(), NetBSD 11's dynamic linker holds its exclusive lock and
  exit() waits for it: the process parks on itself. Fix in
  tools/unixbench/ub.sh: in those two, exit() from a signal handler
  leaves through fflush + _exit, and they bind at load (-z now). (A first
  version made every exit() an _exit, the children's in the timed loop
  too: spawn +16 % on the board, +17 % in QEMU. Not used.) The board
  image's programs must be rebuilt with it (`sh ub.sh build` on the
  guest).

## Area (2026-10-16): 41,528 -> 39,447 ALMs

With branch prediction and FP overlap the FPGA was 99 % full (seed 2:
CPU +0.245 ns, HDMI -0.310). Cuts, each kept only if its benches and the
suites pass:

- sys options in the qsf (sys/ itself untouched): MISTER_DISABLE_ALSA
  (the HPS's Linux audio into the core's output), MISTER_DISABLE_YC
  (composite/S-video), MISTER_DISABLE_ADAPTIVE (the scaler's adaptive
  polyphase filter; every failing HDMI path was in it).
- emc: the 33-bit line compare is shared by the error and the correction
  logic; an entry keeps its corrected data bit and its correctable flag,
  computed once at injection, instead of decoding the syndrome per access.
  (Four entries with the report a cycle late passed tb_emc but failed
  OBP's ECC Multiple CE test on CPU 1 on the board; both reverted.)
- iu: the E/M/W data registers (instruction, pc, operands, results) are no
  longer cleared on reset and flush; the valid, trap and decode bits are.
- cs4231: the rate accumulators scaled by the common factor of the clock
  and the crystals (about 30 bits instead of 40).
- ss20_iobridge: the request is captured as the first beat starts (it
  began a cycle after the request anyway), so the I/O slaves see
  registers instead of the CPU's request path. Besides taking those paths
  off the CPU clock, it saved ~860 ALMs.

Result (seed 2): 39,447 ALMs (94 %), CPU +0.034 ns, HDMI +0.158 ns.
The tightest CPU paths left run from the CPU's memory request through
ss20_mbus into the memory controller and emc.
Board (rbf c118d8d9): post --obp (the ECC tests), cpu 84/0/5, netbsd,
solaris, scsi, cd (93 s), cdaudio, net-netbsd, solaris-obp, stress 10 min
PASS. UnixBench (ub-s6-c1.log) **3.5** (FAST_HIT 3.2): Dhrystone 57.7k lps,
Whetstone 19.9 MWIPS, every test the same or better than ub-lh-c1.

## Area, second pass (2026-10-17): 39,695 -> 36,989 ALMs

The next speed features (fetch recovery after stalls, load-use bubbles,
forward-branch prediction, an L2) had no room at 95 %, so a second area
pass went first. Each change kept its bench green, the CPU suite at 84/0/5 and
the perfbench ticks exactly as above; NetBSD boots under OpenBIOS in the
2-CPU sim. In order of size:

- l1cache: port B's tag write word chosen once and offered to every way,
  the enables pick the way (-745 ALUTs over the two CPUs).
- cpu_module: one doubleword lane shifter (the PA's low bits are the
  VA's), the memory response's data ungated to the walker and both
  caches (ack/err steered), the micro-TLB's duplicate check remembers the
  entry that matched instead of comparing all eight tags at the fill; the
  SuperSPARC breakpoint/counter/ACTION registers (ASI 0x38, 0x49-0x4C) as
  eight 36-bit words in MLAB (an 8-cycle sweep clears them at reset and at
  the watchdog).
- srmmu: tv/tlock/used written through one indexed port each (fill,
  flush sweep and ASI 6 writes are exclusive by state), one priority
  encoder for the victim. A hit's used-mark in the very cycle of a fill is
  dropped (replacement history only).
- ss20_mbus and ss20_msi: read data to every master ungated, the request
  mux as an indexed array read, one write port per TLB vector.
- tcx: the copy's five source doublewords in MLAB. sun_kbd: the 128
  key-down bits in RAM. esp: the 16-byte FIFO in MLAB. emc: what a
  syndrome means from a 256 x 8 ROM, written into the entry a cycle
  after the injection (the board's OBP POST ECC tests pass).
- iu: wr %y/%psr/%wim/%tbr values travel in m_result/w_result, one adder
  for the branch and call targets (-64 registers a CPU, no ALUT change).
- qsf: MISTER_DOWNSCALE_NN (the framework's scaler uses nearest-neighbour
  when the output is smaller than the picture; upscaling untouched):
  -134 ALUTs and 6 DSPs in ascal. A one-line revert if the quality
  matters.

Not kept: `OPTIMIZATION_TECHNIQUE AREA` per chipset entity (no effect).

Result (seed 4, the shrink branch alone, rbf 76101111): **36,989 ALMs
(88 %)**, 37,765 registers, 41 DSPs, **CPU +0.523 ns**, HDMI +0.288 ns.
Board: cpu 84/0/5, netbsd, solaris, scsi, post --obp, solaris-obp PASS
(UnixBench below). Merged with the slavio_timer RUN fix (NeXTSTEP under
the Sun OBP) as main cf549f1: 36,986 ALMs; the fit is seed-sensitive at
